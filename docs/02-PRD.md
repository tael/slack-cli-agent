# slack-cli-agent · PRD

제품 요구사항. 무엇을 만들고 무엇을 만들지 않는가.

전제 — 이 문서는 `01-source-analysis.md` 를 근거로 한다. 거기 적힌 정책 중
회사 전용을 걷어내고 설정으로 외부화한 것이 여기 요구사항이다.

---

## 1. 한 줄 정의

**로컬에 설치된 CLI 에이전트를 슬랙에 연결하는 범용 어댑터.**

슬랙에서 받은 말을 CLI 에이전트에게 전달하고, 그 답을 슬랙 표기로 되돌린다.
어떤 조직에서든 설정 파일만으로 자기 봇을 만들 수 있어야 한다.

---

## 2. 왜 만드는가

원본 봇는 동작하지만 한 조직 한 사람의 환경에 결합돼 있다. 채널 ID, 사용자 ID,
사내 시스템 경로, 사내 도구 목록이 코드에 박혀 있어 다른 환경에서 그대로 돌지
않는다. 홈 경로마저 다른 머신 것이다.

기존 저장소를 범용화하는 방식은 택하지 않았다. 하위 호환을 지키면서 7,199줄
단일 파일을 분해하면 검증 범위가 감당되지 않고, 범용판을 되적용했을 때 원본 봇의
안정성도 보장할 수 없다. 원본 봇는 여러 봇 중 하나일 뿐이므로, 범용판을 먼저
만들고 원본 봇를 나중에 그 위에서 다시 구성한다.

---

## 3. 사용자와 사용 맥락

### 주 사용자 — 봇 운영자

자기 머신에 Claude Code 나 Codex CLI 를 설치해 두고, 팀 슬랙에서 그것을 쓰고
싶은 사람이다. 서버를 운영할 생각은 없다.

요구 — 설정 파일 하나로 봇을 띄운다. 코드를 고치지 않는다.

### 부 사용자 — 슬랙에서 봇을 부르는 사람

봇의 내부를 모른다. 멘션하거나 스레드에서 말을 건다.

요구 — 답이 온다. 안 오면 왜 안 오는지 표시로 안다.

### 운영 환경

macOS 상시 기동을 기준으로 한다(launchd). Linux systemd 는 이후 과제로 둔다.
공인 IP 와 인바운드 포트는 필요하지 않다 — Socket Mode 를 쓴다.

## 4. 범위

### 포함

| 영역 | 내용 |
|---|---|
| 슬랙 연결 | Socket Mode. 멘션·DM·스레드 답글·리액션 수신 |
| 엔진 실행 | 로컬 CLI 를 subprocess 로 호출. Claude·Codex 를 기본 제공 |
| 엔진 플러그인 | 새 엔진 추가가 어댑터 코드 변경 없이 되는 계층 |
| 프로필 | 봇 하나를 정의하는 설정 단위. 한 머신에서 여러 봇 |
| 권한 | 소유자·신뢰·일반의 계층. 읽기 전용이 기본 |
| 세션 | 스레드·채널 단위 세션 유지와 맥락 복원 |
| 출력 | Block Kit 과 mrkdwn 이원화, 안전 분할 |
| 신뢰성 | 캐치업, 건강 감시, 지켜보기 큐, 자가 재기동 |
| 후처리 가드 | 프롬프트로 막히지 않는 것을 코드가 잡는 계층 |
| 리액션 후처리 | 부검·디버그 추적·서식 점검 |
| 관리 명령 | 소유자 전용. 모델을 거치지 않는 즉시 처리 |
| 봇별 확장 | 전용 기능을 플러그인으로 붙이는 확장점 |
| 기동 전 점검 | 정적 검사로 기동 실패를 미리 검출 |

### 제외

- 슬랙 외 메신저(디스코드·텔레그램). 구조는 막지 않되 구현하지 않는다
- 웹 대시보드. 원본 봇에는 있으나 초판에서 제외한다
- 지식 자동 축적(`learn.py`). 이후 과제
- 멀티테넌트 호스팅. 한 머신 한 운영자를 전제한다
- 원격 API 직접 호출. 로컬 CLI 만 부른다

### 명시적 비목표

**원본 봇와의 하위 호환을 지키지 않는다.** 설정 형식도 상태 파일 형식도 새로
정한다.

**신규 기능을 넣지 않는다.** 2026-09-14 사용자 결정 — 바꾸는 것은 코드 구조와
실행 구조이고, 응답 동작과 기술 선택은 원본을 그대로 따른다. 라이브러리
Socket Mode 연결을 유지한다.

**1차 목표에 실행 구조 변경 3가지를 포함한다.**

| 항목 | 내용 |
|---|---|
| Ingress·Worker 프로세스 분리 | 이벤트 수신과 장기 실행을 분리한다 |
| SQLite 영속 작업 큐 | 기계가 쓰는 상태만 DB. 사람이 편집하는 설정은 파일 |
| 단일 파이썬 관리 CLI | 셸 스크립트 6종을 대체한다 |

영속 큐의 부속으로 워커 크래시 감지를 최소 형태로 넣는다. heartbeat 갱신과
정체 작업 재진입까지이고, 레이턴시 SLO 같은 관측 항목은 넣지 않는다.

**프롬프트·페르소나·채널 설정은 파일로 유지한다.** 파일이어야 사람이 편집하고
재기동 없이 반영된다. 원본의 상태 외부화 원칙이 그것이고 실제로 운영에 쓰이고
있다. DB 로 옮기는 것은 큐·세션·감사·부검 기록처럼 기계만 읽고 쓰는 것뿐이다.

설계 검토에서 나온 나머지 개선안(레이턴시 예산 SLO, 소켓
ping-pong 기반 리셋)은 범위 밖이다. 범용판이 안정화된 뒤 별도 과제로 다룬다.

**이유는 검증 때문이다.** 범용판은 최종적으로 원본 봇를 대체한다. 구조와 동작을
동시에 바꾸면 회귀가 났을 때 원인을 구분하지 못한다. 기능이 1대1 로 대응되어야
같은 입력에 같은 출력이 나오는지 대조할 수 있다.

## 5. 핵심 요구사항

### R1. 설정만으로 봇이 정의된다

프로필 파일 하나가 봇 하나를 정의한다. 코드에 조직 고유값이 없다.

프로필이 담는 것 — 이름과 표시명, 엔진과 실행 파일 경로, 모델, 상태 디렉터리,
작업 디렉터리, 소유자 ID, 채널 기본값, 엔진별 세부 설정.

**판정 기준** — 저장소 전체에서 특정 조직의 채널 ID·사용자 ID·사람 이름·내부
시스템 주소를 grep 해 0건이어야 한다.

### R2. 민감 정보가 저장소에 들어가지 않는다

채널 ID, 사용자 ID, 내부 주소, 페르소나 본문, MCP 자격증명은 상태 디렉터리에만
둔다. 저장소에는 예시 파일만 둔다.

**판정 기준** — `.gitignore` 가 봇별 설정 전체를 제외한다. 커밋 전 검사
스크립트가 민감 패턴을 검출한다.

### R3. 엔진이 교체 가능하다

엔진은 인터페이스 하나를 구현하는 클래스다. 새 엔진을 추가할 때 어댑터
본체 코드를 고치지 않는다.

인터페이스가 책임지는 것 — 명령 조립, 실행, 응답 파싱, 세션 식별자 관리,
한도 판정, 사용량 추출.

**판정 기준** — 세 번째 엔진(Gemini 등)을 추가하는 데 필요한 변경이 엔진
모듈 하나와 프로필 설정뿐이다.

### R4. 읽기 전용이 기본이다

기본 권한은 조회만이다. 쓰기 도구는 신뢰 계층에서만 열린다.

**판정 기준** — 기본 프로필로 띄운 봇이 Bash·Edit·Write 를 쓰지 못한다.

### R5. 답을 못 한 요청이 묻히지 않는다

재기동·장애·네트워크 단절로 놓친 요청을 복구한다. 처리 상태가 리액션으로
드러난다.

요청은 접수 시점에 영속 큐에 기록된다. 프로세스가 죽어도 큐에 남고, 워커가
실행 중 죽으면 정체 작업으로 검출해 다시 대기 상태로 되돌린다.

**판정 기준** — 프로세스를 요청 처리 중에 죽였을 때 재기동 후 그 요청이 다시
처리된다. 두 번 답하지 않는다. Ingress 만 죽였을 때 실행 중이던 작업은 영향을
받지 않는다.

### R6. 판정 불가와 부재를 구분한다

조회에 실패한 것을 "없다" 로 세지 않는다. 모르는 값으로 지표를 만들지 않는다.

**판정 기준** — 기록 조회가 빈 결과를 줄 때 재시도하고, 그래도 가릴 수 없으면
재시도 큐에 넣는다. 실행 기록을 못 찾으면 그 항목을 빼지 0 으로 채우지 않는다.

### R7. 지침으로 막히지 않는 것을 코드가 잡는다

프롬프트에 적었는데 지켜지지 않는 것들을 발신 직전에 검출해 보정한다.
보정한 사실을 감사 기록에 남긴다. 조용히 고치지 않는다.

### R8. 상태를 바꾸는 설정이 재기동 없이 반영된다

프롬프트·페르소나·채널 설정·지식은 요청마다 다시 읽는다.

### R9. 기동 전에 실패를 검출한다

프롬프트 파일 누락, MCP 실행 파일 누락, 작업 디렉터리 오류를 기동 전 정적
검사로 잡는다. 검사가 실패하면 기존 프로세스를 유지한다.

### R9-1. 운영 명령이 하나의 CLI 에 모인다

기동·중지·재기동·점검·설정 반영·상태 조회·재처리를 파이썬 CLI 하나로 한다.
셸 스크립트를 늘리지 않는다.

**판정 기준** — 운영자가 쓰는 명령이 전부 그 CLI 의 하위 명령으로 나온다.
설치 문서에 셸 스크립트 경로가 등장하지 않는다.

### R10. 한 머신에서 여러 봇이 돈다

프로필별로 상태 디렉터리·작업 디렉터리·PID 파일·launchd 라벨이 갈린다.
한 봇을 재기동해도 다른 봇에 영향이 없다.

## 6. 기능 요구사항

### 6.1 수신

- 채널 멘션에 응답한다
- DM 에 응답한다. DM 은 본문에 답한다(스레드로 접지 않는다)
- 봇이 이미 참여한 스레드에서는 멘션 없이도 응답한다. 단 채널 설정으로
  멘션 필수로 바꿀 수 있다
- 맞장구·혼잣말에는 응답하지 않는다. 길이가 아니라 어휘로 판정한다
- 봇이 되물은 자리에서 온 말은 짧아도 응답 대상이다
- 첨부 파일을 내려받아 모델이 열 수 있게 한다
- 본문의 슬랙 링크를 어댑터가 먼저 읽어 프롬프트에 싣는다

### 6.2 권한

계층 세 개를 기본으로 둔다.

    owner      프로필에 지정된 소유자. 가장 높은 모델과 effort
    trusted    소유자 DM 또는 지정 채널. 자기 설정 수정까지 가능
    general    나머지. 읽기 전용, 민감 정보 가드 적용

채널 단위로 공개 수준을 조정한다 — 구조 설명 허용 여부, 사용량 노출 여부.

소유자 하한 규칙을 유지한다. 채널 설정값은 다른 사람을 위한 상한이지
소유자의 하한이 아니다.

### 6.3 세션

- 스레드 단위 세션(기본 24시간)과 채널 단위 세션(기본 7일)
- 세션이 없거나 만료되면 슬랙 대화를 읽어 맥락을 다시 세운다
- 세션이 있어도 마지막으로 본 시각 이후의 대화를 더 읽어 붙인다
- 세션 이어가기가 실패하면 새 대화로 한 번 더 시도한다. 단 한도 소진은 제외
- 실행 환경(작업 디렉터리·모델)은 화자가 아니라 대화 단위로 정한다

### 6.4 출력

- 채널별로 Block Kit 과 mrkdwn 을 고른다
- 표·코드블록·인용·목록을 중간에서 자르지 않고 분할한다
- 분할 결과를 검증하고 실패하면 안전 경로로 물러선다
- Block Kit 이 거절되면 평문으로 낮춰 다시 보낸다
- 일부만 전송된 경우 그 사실을 표시한다

### 6.5 상태 표시

리액션으로 상태를 드러낸다.

    처리 중 / 대기 / 완료 / 실패 / 침묵 / 감시로 이관

이모지 이름은 프로필에서 바꿀 수 있어야 한다.

### 6.6 신뢰성

- 슬랙 연결 상태를 주기적으로 확인한다
- 소켓만 깨진 상태를 검출해 스스로 재기동한다
- 재기동 중 잘린 요청을 저장했다가 다음 기동에서 다시 처리한다
- 놓친 요청을 주기적으로 캐치업한다. 한 스레드에 여럿이면 묶어 한 번만 답한다
- "지켜보겠다" 는 약속을 큐에 등록해 프로세스 수명과 무관하게 지킨다

### 6.7 관리 명령

소유자 전용. 모델을 거치지 않는다.

    채널 목록 조회 / 채널 해제
    채널 모드 변경 / 응답량 조절
    엔진 상태 조회 / 엔진 전환 승인 · 거부
    도움말

### 6.8 리액션 후처리

    부검        무엇이 왜 잘못됐는지
    디버그 추적  입력·판단·출력 과정
    서식 점검    표기만 점검하고 원 메시지를 교정

각각 중복 실행을 막고, 중단 시 재시도 가능하게 기록을 되돌린다.

### 6.9 봇별 확장

전용 기능을 플러그인으로 붙인다. 어댑터 본체를 고치지 않는다.

플러그인이 붙일 수 있는 것 — 관리 명령, 시스템 프롬프트 조각, 후처리 가드,
권한 판정 추가 조건.

원본 봇의 사내 워크플로 도구 조작이 이 형태로 옮겨갈 대상이다.

## 7. 비기능 요구사항

### 성능

- 요청 타임아웃 15분. 중앙값 기준 1분 이내 응답을 기대한다
- 동시 처리 상한을 설정으로 둔다. 기본 10
- 같은 스레드의 요청은 순서를 지켜 하나씩 처리한다

### 신뢰성

- 프로세스가 죽어도 처리 중이던 요청이 유실되지 않는다
- 슬랙 API 의 빈 응답을 부재로 판정하지 않는다
- 같은 요청에 두 번 답하지 않는다

### 관측

- 요청마다 감사 기록을 남긴다 — 채널, 사용자, 스레드, 원 메시지 시각,
  첫 반응까지 걸린 시간, 대기 시간, 세션, 모델, effort, 소요, 토큰, 성공 여부
- 코드가 보정한 것은 종류별로 기록한다

### 보안

- 기본 읽기 전용
- 자격증명은 상태 디렉터리에만 둔다
- 비소유자에게는 내부 구조·자격증명·세션 상태를 노출하지 않는다
- 저장소에 조직 고유값이 들어가지 않는다

### 유지보수

- 모듈 하나가 책임 하나를 진다
- 테스트가 정상 import 로 동작한다. AST 파싱으로 함수를 떼어 내지 않는다
- 상수에는 그 값을 정한 근거를 주석으로 남긴다

## 8. 성공 기준

초판이 끝났다고 판정하는 조건이다.

1. 새 조직에서 프로필 파일 하나와 슬랙 앱 설치만으로 봇이 동작한다
2. 저장소에 조직 고유값 grep 결과가 0건이다
3. Claude 와 Codex 둘 다 같은 인터페이스로 동작한다
4. 처리 중 강제 종료 후 재기동에서 그 요청이 한 번만 다시 처리된다
5. 기동 전 점검이 프롬프트 누락과 MCP 실행 파일 누락을 검출한다
6. 한 머신에서 봇 2개를 동시에 띄워 서로 간섭하지 않는다
7. 워커를 SIGKILL 로 죽였을 때 그 작업이 대기 상태로 되돌아가 다시 처리된다
8. 운영 명령이 전부 CLI 하위 명령으로 실행된다

## 9. 단계 구분

### 1단계 — 골격

프로필, 엔진 인터페이스, Claude 엔진, 슬랙 수신, 기본 응답, 출력 변환.
이 단계에서 "슬랙에서 물으면 답한다" 가 성립한다.

### 2단계 — 정책

권한 계층, 세션과 맥락 복원, 상태 표시, 후처리 가드, 관리 명령.

### 3단계 — 신뢰성

영속 작업 큐, Ingress·Worker 프로세스 분리, 크래시 감지, 관리 CLI, 캐치업,
건강 감시, 자가 재기동, 지켜보기 큐.

3단계 전까지는 큐를 사이에 두되 한 프로세스에서 돌린다. 구조를 처음부터
큐 기반으로 잡으므로 분리는 기동 방식 변경으로 끝난다.

### 4단계 — 확장

Codex 엔진, 엔진 전환, 플러그인 계층, 리액션 후처리 3종, 진행 표시.

각 단계마다 기동 전 점검과 테스트를 함께 만든다. 나중에 붙이지 않는다.
