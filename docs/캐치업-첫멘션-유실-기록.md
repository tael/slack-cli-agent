# 재연결·기동 직후 첫 봇 명의 멘션 유실 기록

작성 2026-11-09. 조회는 읽기 전용으로 했다. 표기 규약은 확인(값을 직접 조회)과 추론(코드에서 도출, 직접 확인하지 못함)으로 나눈다.

## 1. 사례

- 사례 1 : 구치파치 재기동 19초 뒤 게시된 봇 명의 멘션. 게시 18:03:55 KST, 소켓 연결 18:03:36. 슬랙 기록에는 글이 있고 처리 표식(eyes, white_check_mark)이 한 번도 붙지 않았다. jobs 행이 없다. 확인
- 사례 2 : 신 마메치 ingress 가 기동한 뒤 받은 첫 이벤트인 봇 명의 멘션. 게시 18:24:03 KST, 소켓 연결 18:21:37. jobs 행이 없고 571.8초 동안 답이 없었다. 롤백 뒤 원본 bot.py 의 캐치업이 18:38:04 에 답했다. 확인
- 공통점 : 봇 명의 글이다. 해당 ingress 프로세스가 기동한 뒤 받은 첫 이벤트다. ingress 로그에 경고, 거부, 접수 실패 줄이 없다. 확인
- 대조 : 프로세스 기동 뒤 첫 봇 명의 이벤트 4건 중 2건이 유실됐고 2건은 정상이었다. 표본이 작아 유실 확률은 추정하지 않는다

## 2. 원인으로 수정한 지점

`SlackBotIdentity._load` 에 잠금이 없었다. 신원은 첫 접근 때 `auth_test` 로 조회한다. 먼저 들어온 스레드가 조회를 기다리는 동안 두 번째 스레드가 빈 신원을 읽으면 `is_mentioned` 가 False 를 돌려 `EventListener.from_app_mention` 이 로그 없이 None 을 반환한다. slack_sdk 는 이벤트마다 스레드 풀에서 리스너를 실행하므로 동시 진입이 가능하다. 단위 재현에서 같은 입력으로 False 가 나왔다. 확인

실제 이벤트 경로에서 이 경합이 발생했다는 직접 증거는 없다. 추론이다. 사람 명의 멘션은 `from_app_mention` 이 신원을 쓰지 않아 이 경합과 무관하다.

수정은 `_load` 를 잠금과 이중 확인으로 감싸고, ingress 기동 때 신원을 먼저 확정하며, 수신 진단 로그를 더한다. 로그로 "수신했으나 버림"과 "수신하지 못함"을 가른다. 후자라면 슬랙 쪽 전달 문제(이전 연결로의 전달, 미전송)가 남는다.

## 3. 캐치업이 회수하지 못한 구조

- 기동 캐치업은 2회다. worker 기동 직후 1회, 그 종료 125초 뒤 2회다. 원본 bot.py 는 기동 5초 뒤와 130초 뒤 2회로, 같은 설계다
- 유예 120초. worker 기동 뒤 올라온 글은 최근 120초 안이면 건너뛴다. 원본과 같은 식이다
- 2회차 이후 정기 회수가 없다. 연결 캐치업은 소켓 세대가 바뀔 때만 돌고, `catchup_retry` 는 이전에 실패한 채널만 다시 본다
- 사례 1 산술 : 1회차 종료 18:03:51.7, 게시 18:03:55.4. 게시가 1회차보다 늦다. 연결 캐치업(18:04:04-18:04:21)은 글 나이가 유예 안이라 건너뛴다. 2회차 시작 18:05:56.7 은 유예 만료 18:05:55.4 보다 늦어 후보가 됐어야 하는데 0건이었다
- 사례 2 : 1회차 종료 18:23:18.9, 게시 18:24:03 이라 1회차 이후다. 2회차(18:25:23.9 시작) 스캔 시각이 유예 만료 18:26:03 보다 이르면 건너뛰고 늦으면 후보다. 채널별 스캔 시각이 로그에 없다

이 문서는 캐치업 설정과 구조를 바꾸지 않는다. 원본과 같은 설계이므로 바꾸려면 별도 이슈와 사람 결정이 필요하다.

## 4. 미확인 지점

- 사례 1 의 2회차 스캔에서 글이 후보에서 빠진 이유. 조사 지점은 `_peer_request` 신원 판정, `has_no_request` 제외, 봇끼리 한도, `worker._admit`
- 2회차 스캔의 채널별 시각. 로그에 없다
- message 이벤트 구독 여부에 따라 같은 글의 app_mention 과 message 경합이 성립하는지
- 슬랙이 이전 연결로 이벤트를 나눠 보내는지. 외부 문서로 확인하지 않았다
