# 패키징 경계 — 설치물과 운영물

사용자 지시(2026-09-15) — "설치 하면 바로 쓸 수 있는 패키징으로 방향성을
잡는다. 따라서, 소스코드 자체와 점점 변경되어 커스터마이즈 되는 영역이 나누어져
관리되어야 한다."

## 무엇을 어디에 두는가

| 구분 | 위치 | 성질 |
|---|---|---|
| 설치물 | `src/slack_cli_agent/` | pip 로 설치·갱신된다. 봇마다 다르지 않다 |
| 설치물(동봉 자료) | 패키지 안의 기본 프롬프트·예시 프로필 | 설치 직후 기동에 필요한 최소값 |
| 운영물(설정) | 프로필 JSON (`profiles/<이름>.json`) | 조직 고유값. 저장소에 안 올린다 |
| 운영물(상태) | 상태 디렉터리 `~/.<봇이름>/` | 프롬프트, 지식, 채널 목록, 기록, DB |
| 운영물(확장) | `Profile.plugins` 가 가리키는 모듈 | 그 조직 전용 명령·권한·프롬프트 조각 |
| 운영물(외부 SaaS 배포 정본) | `slack-apps/<이름>.json` | 슬랙에 실제로 올라간 앱 설정의 사본. 조직 고유값이라 저장소에 안 올린다 |
| 설치물(정책 원천) | `slack-apps/_template.json` | 새 봇이 받을 스코프·이벤트·앱 홈. 봇마다 다르지 않다 |

상태 디렉터리 안의 구성은 `config/paths.py` 의 `StatePaths` 가 단일 출처다.

## 지켜야 할 규칙

- **조직 고유값을 설치물에 두지 않는다.** 채널 ID·사람 이름·회사 문구는 프로필과
  상태 디렉터리에만 둔다. 이미 `RuntimeSettings` 의 기본값이 빈 집합인 것이 그
  이유다
- **운영물을 저장소에 올리지 않는다.** `.gitignore` 가 `profiles/*.json` 과
  `prompts/*.md`, `persona/` 를 막는다. 예시(`*.example.json`)만 올린다
- **설치물 갱신이 운영물을 덮지 않는다.** 기본 자료를 상태 디렉터리에 쓸 때는
  이미 있는 파일을 건드리지 않는다
- **설치물이 운영물의 부재로 기동에 실패하면 그것은 설계 결함이다.** 사람이
  손으로 파일을 만들어야 도는 상태는 "설치하면 바로" 가 아니다
- **외부 SaaS 에 있는 설정도 운영물이다.** 슬랙 앱 설정은 코드와 똑같이 봇의
  동작을 정하는데 이 저장소 밖에 산다. 그래서 봇 3개의 DM 이 꺼진 채로 돌았고
  단위 시험 2325건이 전부 통과했다(sca-1v7). 정본을 `slack-apps/` 에 두어
  작업 트리에서 볼 수 있게 하고, 실제 설정과 어긋났는지는
  `tools/slack-app.py diff` 가 본다. 계약은 `slack/manifest.py` 에 있고
  시험과 그 명령이 같은 것을 읽는다
- **그 대조를 읽는 계기도 운영물이다**(sca-4eo). 어느 봇의 app ID 가 어느
  정본에 대응하는지는 `~/.slack-app-config/registry.json` 에 둔다. 조직
  고유값이라 저장소에 안 넣는다. `tools/slack-app.py audit` 이 그 전체를
  돌고, `local.manifest-audit` 이 매일 10:00 에 그것을 불러 차이를 소유자
  DM 으로 알린다. app ID 를 잃은 봇은 `discover` 로 되찾는다

## 상태 디렉터리 안은 다시 둘로 갈린다

`state_dir` 하나에 성질이 다른 것이 같이 있다. 백업·이전·초기화 기준을 세우려면
이 둘을 갈라야 한다.

    사람이 편집한다    prompts/, persona/knowledge/, channels.json
    기계가 쌓는다      persona/learned/, state.db, audit.jsonl, responses/,
                      proposals/, state.json, bot.pid, engine/, engine_state.json

봇을 다른 기기로 옮길 때 가져가야 하는 것은 앞쪽이고, 뒤쪽은 다시 만들어진다.
지금은 경로만 봐서 그 구분이 드러나지 않는다.

## 지금 어긋난 것 (2026-09-15 조사)

- **설치 직후 기동하지 못한다.** `PromptLibrary` 는 `<state>/prompts/<이름>.md`
  만 읽고, 없으면 `MissingPromptError` 를 낸다. 가드 문구가 빠진 채 답이 나가는
  것을 막는 정책 자체는 유지해야 하지만, 그 기본 문구가 패키지에 없어서 설치
  직후에는 사람이 직접 만들어야 한다
- **패키지에 동봉 자료가 없다.** `pyproject.toml` 에 package data 설정이 없다
- **상태 디렉터리를 처음 세우는 명령이 없다.** `migrate` 는 DB 스키마만 본다.
  프롬프트·지식·채널 목록의 초기 배치를 맡는 진입점(`init` 상당)이 없다
- **프로필 검색 경로의 기본값이 현재 디렉터리다.** 설치해서 쓰는 형태라면 사용자
  설정 위치(`~/.config/slack-cli-agent/` 같은 곳)가 기본이어야 한다
- **슬랙 토큰이 환경변수에만 있다.** `SLACK_BOT_TOKEN` 과 `SLACK_APP_TOKEN` 을
  `os.environ` 에서 직접 읽는다. 봇이 여럿이면 프로세스마다 환경을 갈라 띄워야
  하고, 설정 파일만 보고는 그 봇이 어느 워크스페이스에 붙는지 알 수 없다
- **`StatePaths.profile` 이 남아 있다.** 상태 디렉터리 안에 프로필 경로가
  정의돼 있는데 실제 로드는 `--profile-dir` 에서 한다. 설정의 출처가 둘로 보인다

이 항목들은 기록만 해 둔 것이고 착수 지시는 아직 없다.

## 갈라 놓은 것

- **지식 파일의 두 출처** (2026-09-17, sca-jl4.5). 사람이 쓰는 것은
  `persona/knowledge/`, 학습 배치가 쌓는 것은 `persona/learned/` 다. 파일 이름
  규칙은 같다(`_*.md` 공통, `<채널>.md` 채널별). 프롬프트에는 사람 것이 먼저 오고
  학습 것은 출처를 밝히는 머리말과 함께 뒤에 붙는다.
  가르기 전부터 있던 봇의 옛 파일에는 학습이 붙인 줄이 `persona/knowledge/` 에
  그대로 남아 있다. 계속 실리므로 옮기지 않아도 내용이 사라지지는 않는다. 정정
  항목수 지표는 두 자리를 더해 세므로 가른 날짜에서 수치가 끊기지 않는다.

## 설정에 들어가는 것 (2026-09-15 기준)

프로필 JSON 하나가 그 봇의 전부다. 예시는 `profiles/example.example.json`.

    name, display_name          봇 이름과 표시 이름
    primary_engine/fallback     엔진 타입, 실행 파일, 모델, 소유자용 모델, 옵션, 엔진 홈
    state_dir, work_root        상태 디렉터리와 작업 디렉터리
    data_dir, attach_dir        명부 파일, 첨부 보관
    owner_user_id, owner_dm     소유자
    troubleshoot_channel        보고 채널
    plugins                     조직 전용 확장 모듈 경로
    settings                    RuntimeSettings 덮어쓰기

슬랙 토큰만 여기 없고 환경변수에 있다. 위에 적은 대로 그것은 어긋난 것으로 본다.

## MCP 서버 자격은 프로필이 들고 있지 않는다 (2026-09-17)

프로필은 토큰 키를 재귀로 거부한다. 다만 `mcp_servers.<이름>.env` 는 MCP 서버가
자기 자격을 받는 유일한 경로라 그 검사에서 면제돼 있다. 그래서 그 자리만 평문
자격이 프로필 파일에 남을 수 있었다. 웹 콘솔이 프로필을 읽고 다시 저장하므로
노출 면이 있다 (sca-dn4).

`env` 와 `headers` 값은 간접 표기로 적는다.

    "env": { "GITHUB_TOKEN": "${env:GITHUB_TOKEN}" }
    "env": { "GITHUB_TOKEN": "${file:~/.config/slack-cli-agent/github-token}" }

    ${env:이름}    봇 프로세스의 환경변수에서 읽는다
    ${file:경로}   파일 내용을 읽고 앞뒤 공백을 버린다. ~ 는 홈으로 편다

규칙은 셋이다.

- **값 전체가 표기일 때만 해석한다.** 값 가운데의 표기는 그대로 둔다. 부분 치환을
  허용하면 오타 하나가 자격을 URL 에 끼워 넣고도 아무것도 실패하지 않는다
- **해석은 엔진 명령을 만들 때 한다.** 로드 때 풀면 프로필 객체가 실제 값을 들게
  되고, 그 객체를 다시 저장하는 경로가 원래 문제다
- **못 찾거나 비면 실패로 낸다.** 빈 자격을 넘기면 MCP 서버의 인증 실패로만 보여
  어디서 온 것인지 안 보인다. 기동 점검 `mcp_credentials` 가 같은 것을 먼저 본다

세 엔진이 같은 자리에서 해석한다. 한 엔진만 해석하면 봇의 엔진을 바꾸는 순간
표기가 그대로 서버에 넘어간다.
