# 입출력 절차 v2 설계 (2026-11-19, 페이블 설계)

소유자 8단계 절차(인풋 나열·분류 → 기대 아웃풋 → 조사 인풋 → ack → 실행 →
기대 아웃풋 대비 점검 → 전달)를 내부 처리로 구현하는 설계. 절차는 사용자에게
보이지 않고 ack 와 최종 답만 보인다. 인용 줄은 bbed4047 기준이며 메인이 일부
대조함(plan_gate.py:245-246, 91 / finish_review.py:1857 / plan_start.py:511-519 일치).

## 결론

계획 스키마를 `inputs[{name,value,kind,reason}]` + `output{form,items}` 로 바꾸고, Stop 훅 점검을 `checks` 대조에서 `output` 대조로 바꾸는 설계를 권한다. 본 모델 전달은 기존 PreToolUse 주입을 유지하고, 주입을 못 받은 턴은 Stop 훅 차단 사유로 전달한다. 4단계(요청 재작성)는 모델이 아니라 코드가 조립한다.

## (a) 단계별 데이터 흐름

| 단계 | 만드는 쪽 | 저장 | 본 모델·점검기 전달 |
|---|---|---|---|
| 1-2 입력 목록·분류 | haiku 계획 호출 | `plan.json` 의 `inputs` | 주입문 "입력" 줄 |
| 3 기대 결과 | 같은 호출 | `plan.json` 의 `output` | 주입문 "기대 결과" 줄, 점검기 입력 |
| 4 실행 가능한 요청 | 코드 (`plan_gate.render*`) | 저장 안 함 | 원문 + 입력 표 + 기대 결과를 조립한 주입문 |
| 5 ack | 같은 호출의 `ack` | `plan.ack.json` | `IntakeAck` 그대로 |
| 6 실행 | 본 모델 | transcript | 주입문 규칙 |
| 7 대조 | Stop 훅 새 판정기 | `plan.checks.json` | 불일치 시 차단 사유 |
| 8 전달 | 본 모델 | - | 차단 뒤 재작성 1회 |

주입문에 넣을 6단계 규칙 두 줄:

- `lookup` 입력은 도구로 찾아 채우고 "미확인" 으로 남기지 않는다.
- `guess` 값은 사용자에게 이미 안내됐다. 도구 결과가 다르면 바꾸고, 바꾼 점을 답에 한 문장으로 밝힌다.

늦은 계획과 도구 없는 턴 처리:

- **뒤에 도구 호출이 있는 턴**: 지금 구조 그대로 주입된다.
- **주입 표지가 없는 채 Stop 에 온 턴**: 점검기가 답과 `output` 을 대조한다. 맞으면 통과한다. 다르면 차단 사유에 입력·기대 결과 전체를 실어 1회 재작성시킨다. 이것이 유일한 전달 경로다.
- **Stop 시점에도 `pending` 인 턴**: 기다리지 않고 `skip_plan_pending` 으로 기록만 한다. `decide()` 가 끝난 뒤 계획 파일을 한 번 더 읽는 것까지만 한다.

## (b) 스키마 변경

새 설정 `plan_intake_schema: int = 1` 을 두고, 2일 때 `SCA_PLAN_INTAKE_SCHEMA=2` 로 넘긴다. `environment.py` 통과 목록에 추가해야 한다.

```json
{
  "intent": "한 문장",
  "inputs": [{"name": "날짜", "value": "2026-11-18", "kind": "derived", "reason": "현재 시각 기준 어제"}],
  "ask": "",
  "output": {"form": "한두줄", "items": ["시각", "채널", "요청 요지", "소요 초", "성공 여부"]},
  "ack": "..."
}
```

- **`inputs`**: `assumed` 와 `missing` 을 대체한다. `maxItems` 6. `given` 은 `reason` 을 빈 문자열로 둔다.
- **`kind`**: `given` / `derived` / `lookup` / `guess` / `ask` 다섯 값의 enum 이다.
- **`output.form`**: `한두줄` / `문단` / `목록` / `표` / `긴글` enum 이다. enum 이어야 코드로 형태를 대조할 수 있다.
- **`output.items`**: 짧은 명사구, 최대 6개.
- **없애는 것**: `assumed`, `missing`, `expected_output`, `checks`.
- **밝힐 추정값**: 별도 필드 없이 `kind=guess` 에서 코드가 뽑는다.
- **코드 보정**(`check_intake`): `ask` 종류 입력이 없으면 `ask` 를 비운다. 보정한 사실은 `intake_fixed` 로 기록한다.
- **길이**: `checks`(약 300자)가 빠지고 `inputs` 가 `assumed` 보다 약 200-300자 는다. 순증은 0 근처라는 추정이며 실측이 아니다.

읽는 쪽 호환은 `plan_gate.py` 에 `intake_view(plan)` 를 두어 v1·v2 를 같은 형태로 돌려주게 한다. 이 파일은 표준 라이브러리 단독이고 `pipeline.py:69` 가 이미 import 한다. audit 의 `plan_assumed`, `plan_missing` 키는 view 에서 유도해 유지한다 (`pipeline.py:2177-2195`).

## (c) 7단계 점검기

- **입력**: `output`, `guess` 입력 목록, 답. 도구 근거(`_turn_evidence`)는 넣지 않는다. 형태·항목 대조에는 필요 없고 프롬프트가 짧아진다.
- **코드 선판정**: `한두줄`, `문단` 은 불릿·번호 줄 정규식과 줄 수로 본다. 답 끝 표식과 WATCH 줄은 빼고 센다 (`finish_review.py:1513`).
- **모델 판정 스키마**: `{"missing_items": [...], "unconfirmed_items": [...], "extra": [...최대 3], "undisclosed": [...]}`. 항목별 `basis` 는 두지 않는다.
- **차단 사유 문구**(불일치 시 1회):
    - "기대 결과에 있는데 답에 없는 항목: …"
    - "미확인으로 남긴 항목은 도구로 찾아 채운다: …"
    - "기대 결과에 없는 내용을 뺀다: …"
    - "형태는 … 이다"
    - "추정한 값을 밝힌다: …"
    - 끝에 "도구 결과가 기대 결과와 맞지 않으면 요청을 따르고 사유를 한 문장으로 적는다"
- **상한**: 기존 `SCA_PLAN_CHECK_MAX_BLOCKS` 기본 1을 유지한다. 넘으면 통과시키고 기록한다.
- **건너뛰는 경우**:
    - `ask` 종류 입력이 있는 계획. N9 결함 3과 같은 계열이라 코드 규칙으로 뺀다.
    - 다른 차단이 있거나 남은 시간이 부족한 경우 (`finish_hook.py:228-233` 그대로).
    - 계획이 `ok` 가 아닌 경우.
- **v1 계획**: 기존 `checks` 판정을 그대로 탄다.

- **계획 호출이 요청을 다시 쓰는 `task` 필드**: combined 정제와 같은 일이다. N3 에서 뜻 바꿈 21-36%(v3 4%), p90 +3초였다. 코드 조립으로 대체한다.

- **PostToolUse 주입 추가**: 해당 경우가 35건 중 0건이라 이득 근거가 없다.
- **Stop 훅에서 `pending` 계획 대기**: 빠른 답에 지연만 더한다. 해당은 1건이다.
- **v2 에 `checks` 유지**: 출력이 가장 긴 필드이고 7단계 정의와 다르다. N9 에서 정당한 지적(시간 창, 인용)을 낸 사례는 잃는다.
- **본 모델이 절차를 직접 수행(지침 추가)**: ack 는 haiku, 답은 opus 가 각자 추정해 어긋남이 그대로 남는다.
