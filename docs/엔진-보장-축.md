# 엔진 보장 축 세 가지와 신뢰 경계 결정

`EngineCapabilities`(`src/slack_cli_agent/engine/capability.py:51-55`) 는 엔진이
무엇을 보장하는지를 세 축으로 적는다. 이 문서의 값은 전부 아래 근거 파일과 줄
번호에서 읽은 것이다. 코드를 고치면 같은 자리를 다시 열어 대조한다.

## 축마다 쓸 수 있는 값

축의 값은 enum 이 정한 것뿐이다. 여기 없는 낱말은 그 축의 값이 아니다.

- `tool_restriction` : `none`, `coarse_sandbox`, `exact_allowlist`,
  `all_forbidden` (capability.py:17-26). 약한 것부터의 순서가 그대로 등급이다
- `execution_isolation` : `none`, `workspace_write`, `readonly_sandbox`
  (capability.py:29-32)
- `instruction_boundary` : `unavailable`, `prompt_only`, `native`
  (capability.py:35-40)

## 엔진별 보장

판정에 쓰이는 값은 클래스 선언이 아니라 `capabilities_for(request)` 가 내는
값이다(`engine/runner.py:157`). 기본 구현은 클래스 선언을 그대로 돌려주고
(`engine/base.py:485-487`), claude 와 codex 는 이것을 덮어쓴다.

| 축 | claude | codex | gemini |
|---|---|---|---|
| tool_restriction | 요청이 정한 값 | `coarse_sandbox` 또는 `none` | `none` |
| execution_isolation | `none` | `readonly_sandbox`, `workspace_write`, `none` 중 프로필이 정하는 값 | `none` |
| instruction_boundary | `native` | 첫 턴 `native`, resume 턴 `prompt_only` | `prompt_only` |

근거는 claude.py:188-200, codex.py:119-158, gemini.py:163-167 이다.

### claude 의 도구 축은 요청을 따라간다

`capabilities_for` 가 `request.tools.restriction` 을 그대로 싣는다
(claude.py:194-200). 그 값은 `ToolSelection.access` 에서 나온다 -
`unrestricted`는 `none`, `allowlist`는 `exact_allowlist`, `forbidden`은
`all_forbidden` 이다(`engine/tool_selection.py:21-25`).

닫는 방법은 접근 상태마다 다르다(claude.py:250-270).

- `forbidden` : `--disallowedTools *` 하나만 붙인다. 도구 집합 자체가 비고,
  이 엔진만 `enforces_tool_ban = True` 다(claude.py:182-183, base.py:499-502)
- `allowlist` : `--allowedTools` 로 자동승인을 주고, `--tools` 에 내장 도구
  이름만 넣어 내장 도구 집합을 닫는다(claude.py:267). `--allowedTools` 만으로는
  안 닫힌다 - 2026-09-20 실측에서 `--allowedTools "Read"` 를 주고도 Bash 가
  돌았다(claude.py:258-265)
- MCP 는 `--tools` 가 못 건드리므로 허용목록이 이름을 대지 않은 서버를
  `mcp__<서버>__*` 로 닫는다(claude.py:99-125, 268-270). **끊는 단위는 도구가
  아니라 서버다** - 허용된 이름 하나가 들어 있는 서버는 통째로 열린 채 남고
  그 서버의 다른 도구는 승인 목록에 맡긴다(sca-6ewc)

### codex 의 세 축은 전부 프로필과 턴에 따라 달라진다

`options.sandbox` 값이 격리 축을 정한다(codex.py:119-123, 139-158).

- `read-only` 는 `readonly_sandbox`, `workspace-write` 는 `workspace_write`
- 그 밖의 값은 `none` 이다. **기본값이 `danger-full-access` 라 프로필이 따로
  적지 않으면 격리는 `none` 이다**(codex.py:140). 동봉 프로필 중
  `profiles/example.example.json:14` 만 `read-only` 를 적어 둔다

도구 축은 이 격리에서 파생된다 - 격리가 `none` 이면 `none`, 아니면
`coarse_sandbox` 다(codex.py:154-158). codex 에는 도구 인자가 없어서 도구 축이
샌드박스의 다른 이름인 셈이다.

지침 경계는 resume 턴에서 내려간다. `developer_instructions` 는 세션 첫 턴에
고정돼 새 값을 줘도 원래 것이 유지되므로(2026-09-19 실측, sca-ivs), resume 턴의
이번 턴 지침은 슬랙 입력과 같은 프롬프트 문자열에 실린다 - 그래서
`prompt_only` 다(codex.py:145-152).

### 허용목록을 못 거는 엔진은 문구로 싣는다

`Engine.tool_allow_note`(base.py:536-550) 가 그 문구다. 요청이 `allowlist` 인데
그 턴의 `tool_restriction` 이 `exact_allowlist` 가 아닐 때만 나온다. 허용 이름이
전부 읽기 전용이면 "읽기만 한다" 로, 아니면 이름을 나열한 문구로 나간다. 이름을
대는 쪽이 늘 맞지는 않아서 둘로 나눠 뒀다 - codex 는 셸 하나라 도구 이름이
그쪽에서 뜻을 잃는다.

문구를 싣는 자리는 codex 의 첫 턴 프롬프트(codex.py:237)와 resume
프롬프트(codex.py:259), gemini 의 `-p` 프롬프트(gemini.py:224)다. 도구 금지
문구인 `tool_ban_note`(base.py:514-518)도 같은 자리에 같은 조건으로 붙는다.

**문구는 강제가 아니다**. 축 값은 그대로 두고 감사 기록에도 완화로 남는다.

## 실행 시점에 무엇이 막히는가

`EngineRunner._blocked_response`(runner.py:232-247)는 **세 축을 전부 본다**.
하나라도 요구보다 약하면 `capability_unmet` 으로 `prepare()` 전에 막는다. 축
하나만 강제하면 나머지 둘을 설정하는 것이 뜻이 있는 것처럼 읽힌다는 것이 그
이유다(sca-igu).

요구를 세우는 자리는 `auth/execution_policy.py:32-50` 하나뿐이고, 거기서
채우는 것은 도구 축뿐이다. **나머지 두 축은 아무도 요구하지 않아서 결과적으로
막지 않을 뿐이고, 강제 경로가 없는 것은 아니다**. 요구는
`ExecutionRequirements` 로 실려 온다(`engine/base.py:95`).

완화도 도구 축에만 열려 있다(execution_policy.py:43-49).

- 채널의 `tool_enforcement` 가 `strict` 면 `downgradable_axes` 가 비어 실행이
  막힌다
- 기본값인 `audited` 면 도구 축만 완화 대상이고, **감사 기록이 실제로 남은
  경우에만** 실행된다(runner.py:242-252, sca-gpe)
- 요청이 `unrestricted` 면 요구 자체를 세우지 않는다(execution_policy.py:41-42)

세 축의 실제 값과 요구, 완화 여부는 매 요청 `capability` 감사 기록으로 남는다
(runner.py:311-355).

기동 시 점검도 하나 있다. `preflight/checks.py:305-321` 이 1차와 2차 엔진의
"클래스 선언값" 을 보고 `exact_allowlist` 가 아니면 경고한다. 요청별 값이
아니라 선언값이라 codex 는 `options.sandbox` 와 무관하게 같은 문구가 나온다.

## 신뢰 경계를 강제하지 않는 이유 (2026-09-19 결정, sca-2q6)

**결정 - 강제하지 않고 기록만 유지한다**.

근거 둘이다.

첫째, rei 가 통째로 멈춘다. rei 의 1차 엔진은 gemini 이고
(`profiles/rei.json` 의 `primary_engine.type`) gemini 는 `prompt_only` 다.
강제하면 rei 의 모든 요청이 실행 전에 거부된다. 폴백은 한도 소진에만 걸리므로
2차로 넘어가지도 않는다. 봇 하나가 답을 못 하게 되는 대가로 얻는 것이 기록
한 줄이다.

둘째, 선언할 자리가 없다. `EngineRequest` 를 만드는 세 자리
(`core/pipeline.py:289`, `learning/analyzer.py:169`,
`review/engine_adapter.py:68`)와 검수 경로(`core/application.py:1051`)가 전부
슬랙에서 온 문장을 프롬프트에 넣는다. "비신뢰 입력 있음" 이 상수가 되어
변별력이 없다.

**이 결정을 다시 볼 조건** - gemini 가 시스템 지침을 프롬프트 밖 인자로 받는
경로가 생기면 그때 강제를 검토한다. 그 전에는 축 값과 audit 기록만 둔다.
