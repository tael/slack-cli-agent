# 엔진 보장 축 세 가지와 신뢰 경계 결정

`EngineCapabilities` 는 엔진이 무엇을 보장하는지를 세 축으로 적는다.

| 축 | 뜻 | claude | codex | gemini |
|---|---|---|---|---|
| tool_restriction | 도구를 어느 정도로 제한할 수 있는가 | exact_allowlist | coarse_sandbox | none |
| execution_isolation | 실행을 격리하는가 | none | native | none |
| instruction_boundary | 시스템 지침과 사용자 입력을 분리하는가 | native | native | prompt_only |

## 실행 시점에 강제하는 것은 도구 축 하나다

`engine/runner.py` 의 `TOOL_AXIS` 가 그것이다. 요구 등급을 못 맞추면
`prepare()` 전에 `capability_unmet` 으로 막는다. 나머지 두 축은 audit 에
기록만 한다.

## 신뢰 경계를 강제하지 않는 이유 (2026-09-19 결정, sca-2q6)

**결정 — 강제하지 않고 기록만 유지한다.**

근거 둘이다.

첫째, rei 가 통째로 멈춘다. rei 의 1차 엔진은 gemini 이고 gemini 는
`prompt_only` 다. 강제하면 rei 의 모든 요청이 실행 전에 거부된다. 폴백은
한도 소진에만 걸리므로 2차로 넘어가지도 않는다. 봇 하나가 답을 못 하게
되는 대가로 얻는 것이 기록 한 줄이다.

둘째, 선언할 자리가 없다. `EngineRequest` 를 만드는 세 자리
(`core/pipeline.py`, `learning/analyzer.py`, `review/engine_adapter.py`)가
전부 슬랙에서 온 문장을 프롬프트에 넣는다. "비신뢰 입력 있음" 이 상수가
되어 변별력이 없다.

**이 결정을 다시 볼 조건** — gemini 가 시스템 지침을 프롬프트 밖 인자로
받는 경로가 생기면 그때 강제를 검토한다. 그 전에는 축 값과 audit 기록만
둔다.
