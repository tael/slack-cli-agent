# 캐치업이 접수기 단독 재기동 구간을 회수하지 않는다 — 5why

작성 2026-09-16. 실측 근거는 `~/.shinji/logs/worker.err.log`, `~/.shinji/state.db` 의
jobs 테이블, 측정 스크립트 `~/Jobs/tasks/catchup-ingress-gap-test.py`.

## 1. 문제 정의

- 00:16:25 접수기(local.shinji.ingress) unload. 워커는 계속 실행.
- 00:16:27 `#테스트`(C0C1LNABECV) 에 tael 계정으로 부름 1건 게시(ts 1789485387.422519).
- 00:20:29 접수기 load.
- 00:22:28 jobs 에 등재(id 21). 게시로부터 361초, 접수기 재기동으로부터 119초.
  payload `late=False` — 캐치업이 넣은 것이 아니다(캐치업은 `marked_late()` 로
  `late=True` 를 붙인다).
- 같은 구간 worker.err.log 에 캐치업 실행 기록이 없다. 마지막 기록은 00:05:39.

즉 이 부름을 회수한 것은 이 저장소의 캐치업이 아니라 슬랙의 이벤트 재전달이다.

**대조군** — 00:01:56 게시분(ts 1789484516.419529)은 워커가 00:02:04 에 재기동돼
기동 캐치업이 00:02:52 에 회수했고 payload 는 `late=True` 였다. 워커가 함께
재기동하는 구간에서는 캐치업이 정상 동작한다.

## 2. 반복적 질문

1. **왜 캐치업이 이 부름을 회수하지 않았나** — 그 구간에 캐치업이 한 번도 실행되지
   않았다. 근거: worker.err.log 의 마지막 캐치업 기록이 00:05:39.
2. **왜 실행되지 않았나** — 캐치업 실행 계기가 2개뿐이고 둘 다 성립하지 않았다.
   워커 프로세스 기동(`cli.py:367` 의 `worker.catch_up`, `startup_catchup_runner`)과
   OutageTracker 의 복구 검출(`catchup_retry`) 이다. 워커는 재기동하지 않았고
   OutageTracker 는 끊김을 검출하지 않았다.
3. **왜 OutageTracker 가 끊김을 검출하지 않았나** — 도달성 판정을 `auth_test()` 호출
   성공 여부로 한다(`application.py:1179`). 이것은 워커 프로세스에서 슬랙 HTTP API 로
   나가는 호출이라, 접수기의 소켓이 끊겨 있어도 계속 성공한다.
4. **왜 소켓 상태가 아니라 HTTP 도달성으로 판정하나** — 캐치업과 OutageTracker 가 전부
   `worker_services` 에 있고 소켓은 접수기 프로세스가 갖는다. 워커에는 소켓 상태를 알
   수단이 없다. `ingress_services` 의 `health_runner` 는 소켓 상태를 보지만 재기동만
   하고 캐치업을 부르지 않는다.
5. **왜 소켓을 가진 쪽에 캐치업이 없나** — 원본 마메치(`bot.py`)는 단일 프로세스다.
   소켓 수신·처리·캐치업이 같은 프로세스에 있어 "기동 시 캐치업"(`bot.py:7175`,
   `bot.py:7180` 의 `threading.Timer`)이 곧 "소켓이 새로 붙을 때 캐치업" 이었다.
   이 저장소는 접수기와 워커로 나눴고 캐치업을 워커에 배치하면서 원본이 보장하던
   "소켓 재연결 = 캐치업" 의 등가성이 깨졌다. 프로세스를 나눌 때 그 등가성을 계약으로
   적어 두지 않았다.

## 3. 근본 원인

    표면   접수기만 재기동하면 캐치업이 안 돈다
    근본   캐치업의 발동 조건이 "소켓 공백" 이 아니라 "워커 프로세스 수명" 과
           "워커에서의 HTTP 도달성" 에 묶여 있다. 소켓 공백을 관측하는 주체(접수기)와
           캐치업을 실행하는 주체(워커)가 다른 프로세스인데 그 사이에 신호가 없다

이것을 고치면 같은 계열이 함께 없어진다 — 접수기만 죽는 경우, 네트워크 순단으로
접수기가 소켓을 재연결하는 경우, health_runner 가 접수기를 자기 재기동하는 경우가
전부 같은 원인이다.

## 4. 인과관계 검증

역방향 — 소켓 재연결이 캐치업을 발동시켰다면 이 사고가 났을까. 접수기가 00:20:29 에
소켓을 새로 붙였고 그 시점에 00:16:27 게시분은 유예 120초를 이미 지났으므로 회수
대상이다. 안 났다. 성립한다.

다른 경로 확인 — 이 구간에 코드 변경은 없다. 접수기 unload/load 만 했다. 대조군(워커
동반 재기동)은 회수됐고 실험군(접수기 단독)은 회수되지 않았다.

**아직 유실로 관측되지는 않았다.** 슬랙의 이벤트 재전달이 결과적으로 회수했다.
재전달 횟수를 넘기는 긴 정지에서만 영구 유실이 되는데 그것은 미관측이고 가설이다.
슬랙 재전달을 이 시스템의 보장으로 쓸 수는 없다 — 횟수와 간격이 우리 통제 밖이다.

## 5. 대책

**즉각 조치** — 접수기가 소켓에 붙는 시점에 캐치업이 돌게 한다.

**재발 방지** — 접수기가 소켓 연결·재연결 사건을 워커가 읽을 수 있는 곳(state.db
또는 상태 파일)에 기록하고, `catchup_retry` 가 그 전이를 보고 캐치업을 부른다.
접수기에서 직접 캐치업을 부르는 것보다 낫다. 캐치업 실행 주체가 워커 하나로 유지돼
중복 실행과 동시 enqueue 가 생기지 않고, 접수기는 사실만 남긴다.

**확인 시점과 확인자** — 이 저장소 시험에 "소켓 재연결 전이가 캐치업을 부른다" 를
넣는다. 그 커밋 직후 `tasks/catchup-ingress-gap-test.py` 를 1회 실행해
`late=True` 로 회수되는 것을 확인한다. 확인자는 그 커밋을 낸 세션이다.
